Razorback

A skill set for Claude Code, Codex CLI / ChatGPT desktop app, and OpenCode. It routes every agent and every subagent through Miller instead of grep-and-read chains, dispatches implementation to fresh subagents, and runs an approved plan to completion without waking you for anything short of a real blocker.

Why it exists

Agents re-discover the same code every single time.

AI-assisted development burns tokens on repetitive codebase exploration. The lead orients through a Glob, then a Grep, then a chain of file reads — five to eight calls to answer one question. Then it dispatches a subagent, and that subagent starts from zero and does the same thing. The next one does it again. The work is real, but most of the context spent on it is a re-run of context you already paid for.

Razorback diverged from Superpowers to fix that. It keeps the process discipline and replaces the exploration layer with Miller, a local code-intelligence server that answers orientation questions in one or two structured calls. Three things follow from that choice.

Miller-first, for every worker The lead, implementers, reviewers, and fix workers all orient with search, context, inspect, trace, and impact before any raw file read. On Claude Code a SubagentStart hook injects that ruleset into every dispatched subagent, so a fresh worker cannot fall back to grep by accident.
Delegated execution, inline review Independent tasks go to fresh implementer subagents, in parallel when the plan says they are independent. The lead reviews each result inline for spec compliance and code quality. The lead's own context stays clean, so it can still see the whole change at the end.
Autonomous plan runs Once you approve a plan, execution runs to completion. Stops are gated by a five-category blocker taxonomy, not by task boundaries, and Goldfish checkpoints keep the run durable across a context compaction. The final stop is pull-request creation.

The process

Brainstorm, plan, test, execute, review, finish.

  1. Brainstorm

    Any creative work starts here. The skill pushes back on the first idea, forces the design question into the open, and ends with a written design document plus its visual digest.

  2. Plan

    The design becomes a task-by-task implementation plan with explicit file ownership, verification scopes, and acceptance criteria. You approve the plan. That approval is the gate.

  3. Test

    Test-driven development is the default for features and bugfixes: a failing test first, then the implementation that makes it pass.

  4. Execute

    The plan runs. Which skill drives it depends on the shape of the work — see the fork below.

  5. Review

    The lead reviews every task inline, in two passes: spec compliance, then code quality. An optional pre-merge review by a second model runs after the branch is green.

  6. Finish

    Final branch verification, then the integration decision and the pull request. Merge stays a human action.

The execution fork

subagent-driven-development

Two or more independent tasks, on a harness that can delegate. Fresh implementer subagent per task, parallel where the plan allows, inline review by the lead. This is the primary path.

executing-plans

One task, tightly sequential work, or no delegation available. Single agent, batch execution, same verification scopes.

fixing-small-issues

A defect or tweak that passes objective triage — at most two files, roughly twenty lines, no contract change. Fixed on the current checkout with no worktree and no baseline suite run. It escalates to the standard flow the moment the fix outgrows the criteria.

New in v0.28.0

Every plan gets a picture you can actually read.

A long autonomous run produces a long markdown document, and nobody reads a long markdown document at 8am. So razorback writes a visual digest beside it: a single self-contained HTML file, same basename, that shows the whole run as a timeline. Stage by stage, task by task, with a "you are here" marker on the active task and a warning flag at the exact point where a criterion was revised.

Three moments emit one — brainstorming beside the design document, writing-plans beside the plan, and finishing-a-development-branch beside the final report. The component kit lives in skills/using-razorback/references/digest-kit.md. Digests declare a strict content-security policy: no network fetch, no image, no frame. Setup

Four steps, in this order, starting from nothing.

Razorback is a pure-content plugin — skills, agents, and hooks, with no build step and no runtime dependency. What it does need is Miller and Goldfish, so install those first. Pick your harness and work down the tab.

Claude Code

  1. Node.js

    Miller's plugin launcher is a Node script, so Node.js must be on your PATH. Without it the plugin fails with the opaque MCP error -32000 and writes no log. Install Node.js LTS, then fully restart the agent — an in-session reconnect keeps the old environment and still fails. 

    # Windows, for example
winget install OpenJS.NodeJS.LTS

    On macOS and Linux, install Node.js LTS however you normally do: nodejs.org.

  2. Miller

    Code intelligence. Razorback requires it — there is no fallback to grep.

    /plugin marketplace add anortham/miller
/plugin install miller@miller

  3. Goldfish

    Persistent memory: checkpoints, briefs, and recall. Also required.

    /plugin marketplace add anortham/goldfish
/plugin install goldfish@goldfish

  4. Razorback

    /plugin marketplace add anortham/razorback
/plugin install razorback@razorback

    To scope it to one project instead of your whole user account, add --scope project to the install line. Restart, and the SessionStart hook loads razorback into every new session.

Codex CLI / ChatGPT desktop app

The ChatGPT desktop app was rebranded from Codex. Both use this path.

  1. Node.js

    Miller's plugin launcher is a Node script, so Node.js must be on your PATH. Install Node.js LTS and fully restart the agent. 

    # Windows, for example
winget install OpenJS.NodeJS.LTS

  2. Miller

    codex plugin marketplace add anortham/miller
codex
# then open /plugins and install Miller from the miller marketplace

  3. Goldfish

    codex plugin marketplace add anortham/goldfish
codex plugin add goldfish@goldfish

    Codex does not trust a plugin's hooks automatically. Run codex, open /hooks, trust Goldfish's SessionStart hook, then start a new thread. Until you do, the tools work but the session-start guidance stays silent.

  4. Razorback

    Tell Codex:

    Fetch and follow instructions from https://raw.githubusercontent.com/anortham/razorback/refs/heads/main/.codex/INSTALL.md

    That installs razorback from the repo-scoped marketplace entry, then relies on native skill discovery. Delegated execution needs Codex's multi-agent feature, so add this to your Codex config: 

    [features]
multi_agent = true

    Restart Codex, then check it:

    codex features list | grep '^multi_agent'

OpenCode

  1. Node.js

    Needed only if you install Miller through an agent plugin launcher. The manual binary install path runs miller directly and skips Node entirely.

  2. Miller

    Miller's README documents a plugin one-liner for Claude Code, Codex, and Cursor. For any other MCP harness it points at the same binary plus a routing block: 

    miller rules --harness <name>

    Follow Miller's install guide for the manual binary path and the MCP config block. Do not guess a harness name — the guide lists the supported ones.

  3. Goldfish

    OpenCode loads local MCP servers from opencode.json:

    {
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "goldfish": {
      "type": "local",
      "command": ["bun", "run", "/absolute/path/to/goldfish/src/server.ts"],
      "enabled": true
    }
  }
}

  4. Razorback

    Add razorback to the plugin array in your opencode.json:

    {
  "plugin": ["razorback@git+https://github.com/anortham/razorback.git"]
}

    Restart OpenCode. The plugin registers its own skills directory — no symlinks. To pin a version, append #<version> to the spec; Bun caches by the full spec, so changing the ref forces a fresh fetch.

Copilot CLI gets the ruleset only

No skills, no agents, no delegated execution. Copilot reads .github/copilot-instructions.md natively, so copy razorback's Miller-first ruleset into the repo you work in. If that file already exists, merge the ruleset in rather than overwriting it. 

curl -fsSL https://raw.githubusercontent.com/anortham/razorback/refs/heads/main/.github/copilot-instructions.md \
  -o .github/copilot-instructions.md

Cursor is frozen

Cursor support works as documented and receives no new development. Razorback is not in Cursor's marketplace, so clone the repo and point Cursor at the local checkout through its plugin-load mechanism. 

git clone https://github.com/anortham/razorback.git ~/path/to/razorback
# Then in Cursor: add ~/path/to/razorback to your plugin paths

Honest limits

Two hard requirements, and an uneven harness story.

Miller and Goldfish are mandatory, not suggested. Razorback deleted the generic-tool fallback on purpose. Without Miller the exploration, editing, and reference skills do not function. Without Goldfish there is no durable memory, so a long autonomous run loses its thread at the first context compaction. If you will not install both, this is not the right tool for you.

Support is tiered, and the tiers are real. Three harnesses get the full plugin. Cursor is frozen — it works, but it gets no new work. Copilot CLI gets the Miller-first ruleset and nothing else: no skills, no agents, no delegation. Razorback also owns process contracts only. It never picks your model, and the concrete verification commands come from your repository, not from razorback.
