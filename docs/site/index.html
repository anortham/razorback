Razorback
Why Workflow Practices Skills Setup GitHub

Your coding agent designs first, tests first, and stops at a pull request.

Razorback is a set of skills for Claude Code, Codex CLI / ChatGPT desktop app, OpenCode, and Antigravity. It puts your agent on one workflow: agree on a design with you, write a plan you approve, build it test-first, review it, and open a pull request for you to merge. It can use code-kb to explore code and Goldfish to keep decisions across sessions; both are optional.

What changes when your agent runs razorback

Razorback does not change your model. It gives the agent working rules and a set path, and it makes every subagent follow the same rules.

Area A bare agent With razorback
Exploring code Searches with grep and reads whole files until it finds what it needs. Uses the smallest source of evidence that is enough: a search or a file read for a named file or error, and code-kb for an unfamiliar module. It finds a function's callers before it changes the function.
Subagents Subagents start without your working rules. Each plan task goes to a fresh implementer subagent. On Claude Code, a SubagentStart hook gives every subagent the evidence rules.
Small fixes No rule for how much process a fix gets. A fix of at most two source files and about 20 lines, with no contract change, takes the quick-fix tier: it is fixed on your current checkout and only the affected tests run.
Long plan runs No rule for when to stop, and no saved state when the context compacts. After you approve the plan, the run needs no per-task confirmation. It stops only for five kinds of real blocker. It writes a Goldfish checkpoint for a key decision, a surprising failure, or unfinished work.
Tests Test order and test scope are up to the agent. A failing test comes first on every task. Focused tests run in the inner loop, the full suite runs once at the branch gate, and nothing reruns on an unchanged tree.
Review The agent that wrote the code says it is done. The lead reviews every task against the spec, then for code quality. No "done" or "passing" claim without fresh command output. An optional pre-merge review by codex or claude adds a general pass and a security pass.
Memory across sessions Each session starts from zero. Goldfish checkpoints and briefs keep decisions when Goldfish is installed. Say "resume" and the agent recalls them, reads the plan checkboxes and git log, and continues at the next open task.
Finishing The work ends wherever the agent stops. The run ends at a pull request, with a morning report of every decision it made on its own. Merging stays with you.

Six steps from request to pull request

You make the decisions at the start and the end. The agent does the work in between and tells you what it decided on its own.

  1. Brainstorm

    You
    Answer its questions and decide the choices it names. If it names the wrong path, correct it.
    Razorback
    Runs only when the request is unclear or makes a consequential choice. Names the path first: Spike, Bounded, or Architectural. It writes no code for a consequential choice you have not made. Architectural work gets a written spec in docs/plans/.

  2. Plan

    You
    Reply "approved". "Looks ok" does not start the run. This is your last stop before the agent runs the plan on its own. If you already authorized the work and the plan adds no new choice, the agent records that and does not ask again.
    Razorback
    Writes a plan file only for a handoff, a multi-session effort, or parallel work. The plan states outcomes, the files each task owns, how each task is verified, and acceptance checkboxes; it does not prewrite the code. One coherent task skips this step.

  3. Test

    You
    Nothing. If you do not want TDD, say so; your instructions override the skill defaults.
    Razorback
    Starts every task with a failing test, watches it fail, and then writes the minimal code that makes it pass.

  4. Execute

    You
    Nothing until the end, unless the run hits a real blocker.
    Razorback
    Does one coherent task itself. Gives independent tasks, or tasks that benefit from a separate context, to fresh implementer subagents in parallel. It does not pause between tasks.

  5. Review

    You
    Choose the pre-merge reviewer when you approve the plan: codex, claude, or none. None is the default.
    Razorback
    The lead reviews each task inline, spec first, then code quality. A pre-merge reviewer makes exactly two calls, one general and one security. The lead checks each finding against the current code and fixes the real ones.

  6. Finish

    You
    Read the report, review the pull request, and merge it. If you did not allow push and PR up front, answer one question first.
    Razorback
    Runs the branch gate, including the secrets scan and dependency audit. It writes a morning report to .memories/, pushes, and opens the pull request. It never merges.

Not every change needs the whole trail

The quick-fix tier

A small defect or tweak skips brainstorming when all of these hold:

  • the agent located the target in the current code;
  • at most two source files and about 20 changed lines, tests excluded;
  • no change to a public API, schema, persisted data, config contract, security behavior, or dependency;
  • no new modules or components;
  • one git revert undoes it.

It is fixed on your current checkout, with no worktree and only the affected tests. If a criterion fails or the fix grows, the agent returns to brainstorming triage.

Three brainstorm paths

Spike
A feasibility question. The answer is the output, not kept code. There is no design doc.
Bounded
A change to a flow that already exists, with one or two consequential choices. A short design in chat; the agent waits for your answer only on choices you have not made. No spec file.
Architectural
A new project, subsystem, or interface change. Two or three approaches, an architecture check, a written spec you review, then a plan.

Clear, low-consequence work skips brainstorming. The agent judges by uncertainty and consequence, not by the size of the diff. A path upgrades when hidden complexity appears and downgrades when the task turns out simpler.

Which skill runs the work

subagent-driven-development
Independent tasks, or tasks that benefit from a separate context, when delegation is available. Codex needs multi_agent = true.
executing-plans
A written plan the current agent runs: dependent tasks, no delegation, or your choice of a single agent. One coherent task needs no plan at all.
dispatching-parallel-agents
Ad-hoc parallel work outside a plan.
fixing-small-issues
The quick-fix tier.

Where it stops

After you approve the plan, the run stops for only five reasons:

  1. Credentials, login, or the environment are broken and the plan gives no way to recover.
  2. A destructive action, such as deleting data, a force-push, or a production migration, that the plan did not authorize.
  3. The code contradicts a key assumption of the plan, so its approach no longer works.
  4. A safety-critical choice about security, data integrity, billing, or auth has two plausible readings and the plan does not decide.
  5. Test failures that repeated fix attempts cannot resolve.

The agent decides everything else, such as naming, style, small design choices, or a small bug next to the task, and logs it in the morning report. Its rule: "When in doubt, press on and flag."

The run ends at a pull request. Plan approval allows local commits only, so the agent asks once before it pushes, unless you already allowed push and PR. Merging is yours.

Best practices

Most skills start on their own. These habits get more out of them.

  • Describe small fixes with a measurable scope

    Name the exact thing, for example "the Save button double-submits". The agent announces the quick-fix tier with a file and line count. "Feels simple" is not a criterion.

    Say the Save button double-submits

    fixing-small-issues

  • Let the agent name the path, then correct it

    Before its first question, brainstorming says which path it will take, for example "this looks bounded". That is your moment to override it.

    brainstorming

  • Approve with the word, then walk away

    "approved", "yes, go", or "run it" starts the run. Hedges such as "looks ok" do not. After approval the run does not pause between tasks.

    Say approved

    writing-plans

  • Pick the pre-merge reviewer when you approve

    Name codex or claude in the approval; leave it out for none. Add an ## External model policy block to CLAUDE.md or AGENTS.md so the agent checks the reviewer against it.

    Say approved, codex review

    pre-merge-review

  • Allow push and PR up front for an unattended finish

    Plan approval allows local commits only. Without push and PR authority, the run stops once at the end with Status: Awaiting publication approval.

    finishing-a-development-branch

  • Ask for a second opinion by name

    Name the model you want. "Second opinion from a different model" with no name goes to codex. A claude review is a fresh session of the same model family, so it shares its blind spots.

    Say ask codex get grok's take ask agy

    codex-cli

  • Use convergence for audits and risky decisions

    Your agent and a different model check each other until the findings run out. The loop stops after three rounds and a fixed call budget.

    Say go back and forth until clean doubt this

    cross-model-convergence

  • Say "resume" after a break or a compaction

    The agent recalls its Goldfish checkpoints if Goldfish is installed, reads the plan checkboxes and git log, and continues at the next open task.

    Say resume

    subagent-driven-development

  • Keep test runs scoped

    Focused tests in the inner loop, the full suite once at the branch gate, and never a rerun on an unchanged tree. After a wide failure, rerun only the failing tests, then the wide command once.

    using-razorback

  • Point new library versions at current docs

    For a feature that is new in a version, or a dependency the repo has never used, the agent checks the repo's usage and then the official docs, and cites the URL.

    grounding-in-current-docs

  • Report slowness as slowness, and expect numbers

    No performance change without a before number and an after number. If a fix arrives without them, ask "How much faster?" Performance fixes never take the quick-fix tier.

    Say How much faster?

    diagnosing-performance

  • Mark deliberate shortcuts, then collect them

    Write # razorback: <ceiling>, <upgrade trigger> beside a shortcut. Later, ask for the ledger. A marker with no trigger is flagged no-trigger.

    Say razorback debt what did we defer

    harvesting-debt

  • Cap repeated reviews

    When a review may repeat, or several model CLIs join, the campaign gets a fixed setup, a maximum round count, and a call budget. A closed campaign stays closed, even if findings remain.

    managing-review-campaigns

  • Ask for a digest only if you want one

    A digest is a single-file HTML view of a design, a plan, or a morning report. The agent writes one only when you ask in the session or in your project instructions.

    writing-plans

  • Your instructions come first

    User instructions override skill defaults. If you say "don't use TDD" and your host allows it, the agent follows you.

    using-razorback

The skills

Razorback ships 29 skills. The agent picks most of them from their descriptions; you trigger the second-opinion skills by name.

Start here

  • using-razorback Loads at session start. Lists the skills, matches the process to the task by uncertainty, consequence, and coordination, and holds the code-kb rules.

Design and planning

  • brainstorming Turns an unclear or consequential request into a design you agree with. Scales the ceremony to Spike, Bounded, or Architectural, and asks only about choices you have not made.
  • prototyping Builds throwaway code that answers one design question you settle by hand.
  • writing-plans Turns a spec into a task-by-task plan with file ownership, verification scopes, and acceptance checkboxes.
  • architecture-quality Checks module boundaries, interfaces, and coupling before a plan, for a refactor, or as a cleanup audit.
  • grounding-in-current-docs Checks the repo's usage, then the official docs, before coding against a library version the model may not know.

Execution

  • subagent-driven-development Runs independent plan tasks in fresh implementer subagents, with the lead reviewing each one.
  • executing-plans The default plan runner: the current agent runs an approved plan itself.
  • dispatching-parallel-agents Sends two or more independent problems, such as unrelated test failures, to parallel agents.
  • fixing-small-issues The quick-fix tier: fix on the current checkout and run only the affected tests.
  • using-git-worktrees Lists existing worktrees and branches, then makes an isolated workspace for the task.

Quality and verification

  • test-driven-development Failing test first, watch it fail, then the minimal code to pass.
  • systematic-debugging Finds the root cause before any fix. After three failed fixes, it questions the architecture.
  • diagnosing-performance Measures first, names the cause with a number, and changes one thing at a time.
  • verification-before-completion No "done", "fixed", or "passing" claim without fresh command output.
  • requesting-code-review The checklist the lead applies to each task, plus standalone review for ad-hoc work.
  • receiving-code-review Checks each review item against the code before acting, and pushes back with reasons.
  • security-review Secrets scan and dependency audit at the branch gate, the external-model policy check, and outbound redaction.

Review and ship

  • pre-merge-review Optional review by codex or claude after the branch is green: one general pass and one security pass.
  • managing-review-campaigns Caps repeated or multi-reviewer reviews with a fixed setup, a round limit, and a call budget.
  • finishing-a-development-branch Runs the branch gate, writes the morning report, pushes, and opens a pull request. Stops before merge.
  • harvesting-debt Lists every razorback: shortcut marker with its ceiling, upgrade trigger, and owner.

Second opinions

  • codex-cli Review, second opinion, or delegation through codex exec. The default for "a different model".
  • claude-cli The same through claude -p: a fresh session of the same model family.
  • grok-cli The same through grok -p.
  • agy-cli The same through agy, for Google Antigravity and Gemini.
  • cursor-agent Uses Cursor Agent or Composer as a bounded worker; runs only when you name Cursor.
  • cross-model-convergence Two models check each other in a capped find, verify, fix loop. Includes the pre-build Doubt Pass.

Extending

  • writing-skills Test-driven skill writing: watch subagents fail without the skill, write it, watch them pass.

Setup

Before you start

Razorback works with native tools alone. Two optional MCP servers add to it:

  • code-kb for symbol lookup, callers, and likely tests in unfamiliar code. It needs Node.js 18 or newer on your PATH.
  • Goldfish for decision and handoff checkpoints, briefs, and recall. It needs Bun 1.0 or newer.

Razorback itself is pure content: no build step and no runtime dependencies.

Claude Code

  1. Install code-kb

    Send these as two separate prompts:

    /plugin marketplace add anortham/code-kb
/plugin install code-kb@code-kb

  2. Install Goldfish

    /plugin marketplace add anortham/goldfish
/plugin install goldfish@goldfish

  3. Install razorback

    /plugin marketplace add anortham/razorback
/plugin install razorback@razorback

    For one project only, add --scope project to the install line. Restart, and the SessionStart hook loads razorback into every new session.

    To work on razorback itself, load a local clone:

    git clone https://github.com/anortham/razorback.git
claude --plugin-dir /path/to/razorback

  4. Update

    Turn on automatic updates:

    /plugin marketplace update razorback --auto

    Or update once by hand:

    /plugin marketplace update razorback
/plugin install razorback@razorback

Codex CLI & ChatGPT desktop app

The ChatGPT desktop app was rebranded from Codex. Both use these steps.

  1. Install code-kb

    codex plugin marketplace add anortham/code-kb
codex plugin add code-kb@code-kb

    Codex does not trust plugin hooks by default. Run codex, open /hooks, and trust the two code-kb hooks.

  2. Install Goldfish

    codex plugin marketplace add anortham/goldfish
codex plugin add goldfish@goldfish

    Then trust Goldfish's SessionStart hook in /hooks.

  3. Install razorback

    Tell Codex:

    Fetch and follow instructions from https://raw.githubusercontent.com/anortham/razorback/refs/heads/main/.codex/INSTALL.md

    This installs the razorback plugin from the repo-scoped marketplace entry. Delegated execution needs multi-agent support, so add this to ~/.codex/config.toml:

    [features]
multi_agent = true

    Restart Codex, then check it:

    codex features list | grep '^multi_agent'

  4. Update

    codex plugin marketplace upgrade
codex plugin remove razorback@razorback
codex plugin add razorback@razorback

  5. Fallback: local clone

    If you do not use the plugin, clone razorback and link its skills:

    git clone https://github.com/anortham/razorback.git ~/.codex/razorback
mkdir -p ~/.agents/skills
ln -s ~/.codex/razorback/skills ~/.agents/skills/razorback

    On Windows, in PowerShell:

    New-Item -ItemType Directory -Force -Path "$env:USERPROFILE\.agents\skills"
cmd /c mklink /J "$env:USERPROFILE\.agents\skills\razorback" "$env:USERPROFILE\.codex\razorback\skills"

OpenCode

  1. Add code-kb

    Point OpenCode at your code-kb binary in opencode.json:

    {
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "code-kb": {
      "type": "local",
      "command": ["/absolute/path/to/code-kb", "serve"],
      "enabled": true
    }
  }
}

  2. Add Goldfish

    {
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "goldfish": {
      "type": "local",
      "command": ["bun", "run", "/absolute/path/to/goldfish/src/server.ts"],
      "enabled": true
    }
  }
}

  3. Install razorback

    Tell OpenCode:

    Fetch and follow instructions from https://raw.githubusercontent.com/anortham/razorback/refs/heads/main/.opencode/INSTALL.md

    Or add razorback to the plugin array in opencode.json, globally in ~/.config/opencode/opencode.json or in your project:

    {
  "plugin": ["razorback@git+https://github.com/anortham/razorback.git"]
}

    Restart OpenCode, then ask "Tell me about razorback." to check it loaded.

  4. Update

    To pin a version, add #<version> to the plugin spec. To update, change the tag and restart. If OpenCode keeps an old copy, clear its cache and restart:

    rm -rf ~/.config/opencode/node_modules/razorback

Antigravity

  1. Install code-kb

    agy plugin install https://github.com/anortham/code-kb

  2. Add Goldfish

    agy mcp add goldfish bun run /absolute/path/to/goldfish/src/server.ts

  3. Install razorback

    Clone razorback and import it as a plugin:

    git clone https://github.com/anortham/razorback.git
agy plugin import /path/to/razorback

    Or link the skills globally, for the CLI and the IDE:

    git clone https://github.com/anortham/razorback.git ~/source/razorback
mkdir -p ~/.gemini/config/skills
ln -s ~/source/razorback/skills/* ~/.gemini/config/skills/

    Or link them into one project only:

    mkdir -p .agents/skills
ln -s /path/to/razorback/skills/* .agents/skills/

  4. Update

    Pull the latest changes. If you used agy plugin import, import again:

    cd /path/to/razorback && git pull
agy plugin import .

Copilot CLI gets the rules only

No skills, no agents, and no delegated execution. Copilot reads .github/copilot-instructions.md, so copy razorback's rules into your repo. If the file already exists, merge the rules into it.

curl -fsSL https://raw.githubusercontent.com/anortham/razorback/refs/heads/main/.github/copilot-instructions.md \
  -o .github/copilot-instructions.md

Cursor is frozen

Cursor support works as it is and gets no new work. Razorback is not in Cursor's marketplace, so load a local clone.

git clone https://github.com/anortham/razorback.git ~/path/to/razorback
# Then in Cursor: add ~/path/to/razorback to your plugin paths
