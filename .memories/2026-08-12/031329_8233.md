## Added the `diagnosing-performance` skill

Razorback had no performance skill. `systematic-debugging` listed "Performance problems" in its
When-to-Use block and then gave no method for them — the four debugging phases assume a defect
with a wrong answer, but a slow system returns the right answer too late.

**What landed** on `feat/diagnosing-performance`:

- `skills/diagnosing-performance/SKILL.md` — iron law, four phases, 15-row red-flag table
- `skills/diagnosing-performance/bottleneck-catalog.md` — 8 layers, ~65 rows, each with a
  confirmation step: database, async/concurrency, network, algorithms, memory, caching,
  startup/build/test-suite, client
- `skills/diagnosing-performance/measurement-playbook.md` — workload rules, layer split,
  counting over timing, per-stack tools, ranked regression guards
- `skills/systematic-debugging/SKILL.md` — routes slowness out; "Performance problems" removed
  from its issue list
- `tests/diagnosing-performance.test.mjs` — 20 guard tests
- `README.md` — skill table row

**Key decisions:**

- **Scope is diagnosis only.** Design-time performance budgets and a review-time performance
  lens were both considered and cut. Budgets belong with `writing-plans`, not a diagnosis loop.
- **The law is `NO PERFORMANCE CHANGE WITHOUT A BEFORE NUMBER AND AN AFTER NUMBER`.** Reading
  code is allowed as evidence for a *hypothesis* (an N+1 in a loop is visible without a
  profiler) but never as evidence that the fix *worked*. A stricter profile-before-hypothesis
  law was rejected: the after-number requirement already catches a wrong hypothesis, so the
  strict rule only taxes the cheap wins.
- **Counting beats timing** throughout — query counts are deterministic, assertable in CI, and
  do not flake the way wall-clock thresholds do.

**Impact:** an agent meeting a slow endpoint now has a method instead of a guess. The catalog is
the reusable half; the law is the half that stops speculative caching and parallelism.
