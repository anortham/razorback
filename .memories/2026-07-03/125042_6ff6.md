## Simplified Razorback policy and model selection

### WHAT

Removed `RAZORBACK.md` from the Razorback repo and updated the active skill/docs surfaces so they no longer require a separate project-policy file or model-routing table.

### WHY

The extra policy file duplicated harness instructions and made subagent dispatch more complex than the workflow needs. The user explicitly preferred letting the lead agent decide when to override models instead of baking model-routing tiers into Razorback.

### HOW

- Deleted `RAZORBACK.md`.
- Updated `README.md`, `skills/using-razorback/SKILL.md`, `skills/writing-plans/SKILL.md`, `skills/subagent-driven-development/SKILL.md`, Codex tool mapping, execution/review skills, and CLI helper skills to use active project instructions plus the approved plan as the policy source.
- Removed required `Model Routing` sections, model tiers, worker model-tier prompt fields, and RAZORBACK.md references from current workflow docs.
- Adjusted Claude/Gemini/Codex CLI helper docs so env vars are optional explicit overrides and default behavior inherits the configured CLI/harness model.
- Updated tests so quick-fix scoped verification and architecture-quality lead duties live in their owning skills instead of RAZORBACK.md, and added a regression test that planning/dispatch no longer require Razorback-owned model routing.

### IMPACT

Razorback keeps the parallel execution contract, verification hierarchy, blocker handling, and lead-owned architecture review while removing a duplicated policy layer. Subagent model selection is now intentionally lightweight: use the harness default unless the user, environment, or lead chooses otherwise.
