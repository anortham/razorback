## README accuracy pass + GitHub Pages landing page

Two independent deliverables landed on `worktree-docs-site-2026-08` at `9f276d2`, both built by parallel implementers with inline lead review.

### WHAT

**Part 1 — README.md.** Closed five confirmed drifts left by v0.28.0:
- Added the `harvesting-debt` row. The Skills table is now 26 rows for 26 directories under `skills/`, verified by a sorted name-for-name diff.
- Added a **Visual digest** block under Workflow naming `skills/using-razorback/references/digest-kit.md` and the three read moments that emit one: `brainstorming` (User Review Gate), `writing-plans` (plan-save announcement), `finishing-a-development-branch` (morning report). Proved by `tests/digest-wiring.test.mjs`, whose `WIRING` array pins exactly those three.
- Renamed **Prompt Templates** to **Prompt templates and scripts**; added `sdd-workspace`, `task-brief`, `review-package`.
- Named `writing-good-tests.md` in the TDD row (`testing-anti-patterns.md` is gone).
- Rewrote the `security-review` and `finishing-a-development-branch` rows against their current skill files.
- Added a website link under the title.

**Part 2 — `docs/site/`.** A single-page site plus `.github/workflows/pages.yml`. Hand-written `index.html`, `style.css`, `script.js`, `404.html`, `.nojekyll`, and a copy of the logo SVG.

### WHY

v0.28.0 shipped 15 tasks and the README never moved with them, so it under-reported the skill set and never mentioned the headline feature. Separately, the user wants to recommend razorback to coworkers, and a repo README is poor first contact for someone deciding whether to adopt a workflow.

### HOW

- **Mechanism copied from the Miller repo**, which already deploys hand-written files from `docs/site/` via `upload-pages-artifact`. Same layout, same workflow shape, plus a `workflow_dispatch` trigger. No Jekyll, no framework, no build step — razorback stays a pure-content plugin. Only `docs/site` is uploaded, so `docs/plans/` and `docs/specs/` stay unpublished.
- **Scope ruling:** landing page only. A generated per-skill reference was rejected because it needs a build step.
- **Content ruling:** the full ordered setup path lives on the page — Node.js, Miller, Goldfish, razorback — because both MCP servers are hard requirements and a coworker who installs razorback alone gets a broken experience.
- **Design ruling:** Miller's structural CSS conventions with razorback's own palette from its logo (crimson `#B31B1B`, ink `#141418`, cream `#FFF4E0`), so the sites read as a family without being confusable.
- **Every command on the page is copied from a source of truth**, never reconstructed: this repo's `README.md` / `.codex/INSTALL.md` / `.opencode/INSTALL.md`, or the Miller and Goldfish READMEs. Spot-checked against the upstream files during review.

### IMPACT

- The README no longer misrepresents what ships.
- The site is ready but **not yet live**: GitHub Pages source must be set to **GitHub Actions** in the repo settings, which an agent cannot do.
- Not yet pushed. No PR yet.
- One acknowledged gap: Miller's README gives plugin one-liners for Claude Code, Codex, and Cursor only, so the OpenCode path quotes the generic `miller rules --harness <name>` and links Miller's install guide rather than guessing a harness name. That is the one place a coworker cannot finish from the page alone.
