## Aligned Codex and Claude/OpenCode execution guidance

### WHAT
Updated the core Razorback skill/docs set so Codex, Claude Code, and OpenCode now describe distinct execution paths without contradicting each other.

- Fixed Codex subagent lifecycle guidance in `skills/subagent-driven-development/SKILL.md`
- Corrected the Codex tool mapping in `skills/using-razorback/references/codex-tools.md`
- Expanded `.codex/INSTALL.md` to include Goldfish alongside Julie and to verify `multi_agent`
- Added an explicit Claude-only guard to `skills/team-driven-development/SKILL.md`
- Removed the misleading claim that subagent-driven development was deprecated

### WHY
The repo already intended Codex and OpenCode to use `subagent-driven-development`, but the docs still contained stale Codex API wording (`session_id`, `wait`) and a Claude-centric comparison that implied the non-Claude primary path was obsolete. That would cause long autonomous runs to fail or confuse the harness split.

### HOW
Used the live Codex tool surface plus local CLI help to ground the change:

- Verified current Codex CLI feature support with `codex features list`
- Updated docs to use agent ID semantics with `send_input`, `wait_agent`, and `close_agent`
- Clarified that Agent Teams are Claude Code only, while Codex/OpenCode use subagent-driven execution
- Added Goldfish as a required Codex prerequisite to match Razorback's autonomous execution model
- Ran `git diff --check` and targeted `rg` checks for stale Codex lifecycle terms

### IMPACT
The three main harnesses now have a cleaner story:

- Claude Code: persistent Agent Teams
- Codex: subagent-driven execution with the correct lifecycle calls
- OpenCode: subagent-driven execution without Claude-only team leakage

This reduces the chance of a plan-approved overnight run failing because Razorback handed Codex the wrong agent-control recipe.
